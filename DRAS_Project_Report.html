§ 1

Project Overview

DRAS (Disaster Resource Allocation System) is a full-stack web application that manages the supply chain of essential resources — food, water, medicine, shelter materials — during disaster events. It models the real-world workflow where a relief camp requests supplies, a control center admin approves them, and a warehouse manager dispatches them from stock.

The entire system is backed by a MySQL 8 relational database with carefully defined constraints, stored procedures for every state change, triggers for automation, and role-based MySQL users that enforce access control at the database level — not just the application level.

Key Goals

  • Prevent double-spending of limited relief stock using ACID transactions with row-level locking.
  • Enforce a strict workflow — resources can only move through defined states (Pending → Approved → Dispatched → Delivered).
  • Log every state change automatically via database triggers so there is always a full audit trail.
  • Alert warehouse managers automatically the moment stock drops below a safe minimum threshold.
  • Restrict what each user role can do — warehouse managers cannot approve requests; camp officers cannot modify inventory.
Why stored procedures?  Every mutation (approve, dispatch, confirm, restock) is wrapped in a stored procedure rather than a direct SQL statement from the application. This means triggers always fire, audit logs always record, and no application bug can leave the data in an inconsistent state.

System Architecture

The system is split into three layers that communicate in a clean, one-direction flow. The browser never talks directly to MySQL — all data access goes through the Express API.

① Frontend (React)

  • React 18, runs on port 5173
  • Built with Vite
  • Three dashboards: Admin, Camp Officer, Warehouse Manager
  • All data fetched via /api/… endpoints
  • No direct database access

② Backend (Express)

  • Node.js + Express 4, port 3001
  • All /api/… routes in server.js
  • Uses mysql2 for connection pooling
  • Mutations call stored procedures
  • Returns JSON responses

③ Database (MySQL)

  • MySQL 8.0+, database name: DRAS
  • 13 tables, fully normalized (BCNF)
  • 4 stored procedures
  • 4 triggers, 6 views, 3 SQL functions
  • 3 MySQL application users (RBAC)

Data Flow

The browser sends an HTTP request (e.g. POST /api/requests/5/approve). Express receives it, validates the input, then calls the appropriate MySQL stored procedure (CALL sp_Approve_Request(5)). The procedure runs inside a transaction, updates the tables, fires any relevant triggers, and either commits or rolls back. Express returns the result as JSON to the browser. 

Browser  →  POST /api/requests/5/approve
Express  →  CALL sp_Approve_Request(5)
MySQL    →  BEGIN TRANSACTION
         →  SELECT … FOR UPDATE   (lock the row)
         →  CHECK stock availability
         →  UPDATE Request SET Status = 'Approved'
         →  TRIGGER fires → INSERT INTO Audit_Log
         →  COMMIT
Express  →  { "message": "Approved" }
Browser  →  UI refreshes

How a Request Works — End to End

A resource request goes through exactly four steps, each performed by a different role. No step can be skipped — the stored procedures enforce the valid state transitions.

Camp Officer
1. Raise Request
INSERT → Request + Request_Details
→
Control Admin
2. Approve
sp_Approve_Request(req_id)
→
Warehouse Mgr
3. Dispatch
sp_Dispatch_Request(req_id, w_id)
→
Camp Officer
4. Confirm
sp_Confirm_Delivery(dispatch_id)

Step-by-step detail

#WhoWhat happensTables affectedFinal status
1 Camp Officer Fills a form — chooses resources and quantities, sets priority (Low / Medium / High / Urgent). The app inserts one row into Request and one row per item into Request_Details. Request, Request_Details Pending
2 Control Admin Reviews the request on the dashboard. Clicks Approve. The procedure checks if there is enough combined stock across all warehouses. If yes, it sets Approved_Qty = Requested_Qty for every line item and marks the request Approved. The audit trigger fires automatically. Request, Request_Details, Audit_Log Approved
3 Warehouse Mgr Sees the approved request in their queue. Clicks Dispatch. The procedure verifies that this specific warehouse has enough stock, deducts the quantities from Warehouse_Inventory, and creates a row in Dispatch_Log with an estimated arrival time. The inventory trigger fires and may create a Stock_Alert if stock drops below minimum. Request, Warehouse_Inventory, Dispatch_Log, possibly Stock_Alert, Audit_Log Dispatched
4 Camp Officer When supplies arrive, clicks Confirm. The procedure records the actual arrival time in Delivery_Status, marks the Dispatch_Log entry as Delivered, and sets the Request to Delivered. Dispatch_Log, Delivery_Status, Request, Audit_Log Delivered

§ 5

Stored Procedures

All four procedures follow the same pattern: start a transaction, lock the relevant rows with SELECT … FOR UPDATE, validate the state, make the changes, and then either commit or roll back if anything goes wrong.

sp_Approve_Request (p_Req_ID)

Called by the Control Admin to approve a pending request.

StepWhat it doesWhy
1Locks the Request row with FOR UPDATEPrevents two admins from approving the same request simultaneously
2Checks Status = 'Pending'Cannot approve something already approved or cancelled
3Calls fn_Total_Stock for every line itemChecks if combined stock across all warehouses is enough
4Sets Approved_Qty = Requested_Qty on all line itemsLocks in the quantities to be dispatched
5Sets Request.Status = 'Approved'Moves request to the next stage
6COMMITAll or nothing — if any step fails, the whole transaction rolls back

sp_Dispatch_Request (p_Req_ID, p_W_ID)

Called by the Warehouse Manager to dispatch goods from a specific warehouse.

StepWhat it doesWhy
1Locks the Request rowPrevents double-dispatch
2Checks Status = 'Approved'Can only dispatch approved requests
3Calls fn_Check_Stock for every line item against this warehouseEnsures the chosen warehouse can fulfil the whole order
4Deducts quantities from Warehouse_InventoryReduces physical stock — triggers may fire a Stock_Alert
5Inserts a row in Dispatch_Log with ETACreates the shipment record with estimated arrival time
6Sets Request.Status = 'Dispatched'Moves request forward
7COMMITAtomic — stock deduction and dispatch log always happen together

sp_Confirm_Delivery (p_Dispatch_ID, p_Received_By)

Called by the Camp Officer when the goods physically arrive at the camp.

StepWhat it doesWhy
1Locks the Dispatch_Log rowPrevents duplicate confirmations
2Updates Dispatch_Log.Status = 'Delivered'Marks the shipment as complete
3Inserts into Delivery_Status with actual arrival time and receiver namePermanent delivery record
4Sets Request.Status = 'Delivered'Closes the request lifecycle
5COMMITAll three updates are atomic

sp_Restock (p_W_ID, p_Res_ID, p_Qty, p_Supplier)

Called by the Warehouse Manager to add stock for a resource.

StepWhat it doesWhy
1Inserts into Restock_LogKeeps a permanent record of the restock event
2UPSERT into Warehouse_Inventory — inserts if new resource, otherwise adds to existing quantityHandles both new stock and top-up of existing stock
3COMMITLog and inventory update always happen together
The inventory update triggers trg_after_inventory_restock, which automatically marks any open Stock_Alert as resolved if quantity is now above threshold.
§ 6

Triggers

Triggers are automatic actions the database takes when a specific event happens on a table. No application code needs to call them — MySQL fires them on its own.

Trigger NameFires WhenWhat it does
trg_after_inventory_update AFTER UPDATE on Warehouse_Inventory If NEW.Quantity < NEW.Min_Threshold AND the old quantity was at or above the threshold, inserts a new row into Stock_Alert. This means an alert fires exactly once when stock first crosses the threshold downward — not on every update.
trg_after_inventory_restock AFTER UPDATE on Warehouse_Inventory If NEW.Quantity >= NEW.Min_Threshold AND the old quantity was below the threshold, marks all open alerts for that warehouse/resource as resolved by setting Resolved = TRUE and Resolved_At = NOW().
trg_before_request_details_insert BEFORE INSERT on Request_Details Checks that the parent Request is still in 'Pending' status. If someone tries to add items to an already-approved request, the trigger raises an error and blocks the insert. This enforces workflow integrity.
trg_after_request_status_update AFTER UPDATE on Request When the Status column changes, inserts a row into Audit_Log capturing the old status, new status, the MySQL user who made the change, and the timestamp. This provides a complete, tamper-proof history of every status transition.
§ 7

SQL Functions

Three utility functions are used inside stored procedures to keep the procedure logic clean and reusable.

FunctionParametersReturnsUsed inWhat it does
fn_Check_Stock Res_ID, W_ID INT sp_Dispatch_Request Returns the current quantity of a specific resource in a specific warehouse. Returns 0 if no row exists.
fn_Total_Stock Res_ID INT sp_Approve_Request Returns the total quantity of a resource summed across all warehouses. Used for approval because we approve based on overall availability, not any single warehouse.
fn_Calculate_ETA Distance_Km DATETIME sp_Dispatch_Request Estimates arrival time based on distance. Formula: NOW() + (distance / 25 + 2) hours — assumes 25 km/h average speed plus 2 hours of loading/admin time.

Role-Based Access Control

Three MySQL application users are created with precisely the minimum permissions each role needs. This is security enforced at the database level — even if the Express application had a bug, the database would still reject unauthorized operations.

MySQL UserPasswordRolePermissions
cc_admin cc_pass123 Control Admin GRANT ALL PRIVILEGES ON DRAS.* — full read/write access to all tables and procedures
camp_officer camp_pass123 Camp Officer SELECT on vw_Active_Requests, vw_Current_Inventory
INSERT on Request, Request_Details
EXECUTE on sp_Confirm_Delivery
Cannot UPDATE Warehouse_Inventory or Request directly — only through procedures
warehouse_mgr wh_pass123 Warehouse Manager SELECT on vw_Current_Inventory, vw_Active_Requests
EXECUTE on sp_Dispatch_Request, sp_Restock
Cannot directly UPDATE or DELETE from Warehouse_Inventory or Request
Why this matters: The camp_officer user has INSERT permission on the Request table but cannot UPDATE its Status column. Status changes only happen through stored procedures, which are owned by a higher-privileged user. This means a camp officer cannot self-approve their own request even if they tried.

ACID Compliance & Concurrency Safety

The most critical concurrency problem in a system like this is two admins simultaneously approving two requests that together exceed available stock. Without proper locking, both could read "stock is sufficient" and both approve, leading to a stock deficit when dispatch happens.

How DRAS solves this

Row-level locking with SELECT … FOR UPDATE
When sp_Approve_Request starts, it immediately locks the Request row with SELECT … FOR UPDATE. This means if two approvals are triggered at the same millisecond, one of them will block and wait for the first to finish. By the time the second one reads the stock level, it sees the updated numbers — so it cannot double-approve against the same stock.
ACID PropertyHow DRAS enforces it
Atomicity Every procedure wraps its changes in START TRANSACTION … COMMIT. If anything fails (e.g., insufficient stock, wrong status), ROLLBACK fires and nothing is written. The database never ends up half-updated.
Consistency Table-level constraints (CHECK, NOT NULL, UNIQUE, FK) and trigger guards ensure the data always follows business rules. For example, Approved_Qty can never exceed Requested_Qty, and items cannot be added to a non-Pending request.
Isolation SELECT … FOR UPDATE inside transactions provides row-level isolation. Concurrent approvals and dispatches cannot interfere with each other.
Durability MySQL InnoDB engine writes committed transactions to disk. A server crash after a COMMIT will not lose the data.

§ 14

Normalization Analysis

All 13 tables in DRAS satisfy Boyce-Codd Normal Form (BCNF). The analysis below demonstrates this for the five most complex tables. The remaining eight tables are trivially normalized because each has a single-column primary key and no multi-valued or transitive dependencies.

BCNF rule: For every non-trivial functional dependency X → Y in a relation, X must be a superkey (i.e., X alone can uniquely identify every row in the table). If this holds for all FDs, the table is in BCNF.

1. Request

Functional DependencyLeft side is superkey?Verdict
Req_ID → CC_ID, Camp_ID, Priority, Status, Request_TimeYes — Req_ID is PK✓ BCNF

No partial or transitive dependencies exist. Priority and Status depend only on Req_ID, not on each other or on Camp_ID.

2. Request_Details

Functional DependencyLeft side is superkey?Verdict
Req_Detail_ID → Req_ID, Res_ID, Requested_Qty, Approved_QtyYes — Req_Detail_ID is PK✓ BCNF
(Req_ID, Res_ID) → Requested_Qty, Approved_QtyYes — (Req_ID, Res_ID) is a candidate key✓ BCNF

There is no dependency of Approved_Qty on Requested_Qty — they are independently set at different stages of the workflow. The CHECK constraint (Approved_Qty ≤ Requested_Qty) is a domain constraint, not a functional dependency.

3. Warehouse_Inventory

Functional DependencyLeft side is superkey?Verdict
Inv_ID → W_ID, Res_ID, Quantity, Min_ThresholdYes — Inv_ID is PK✓ BCNF
(W_ID, Res_ID) → Quantity, Min_ThresholdYes — (W_ID, Res_ID) is a candidate key (UNIQUE constraint)✓ BCNF

This table resolves the M:N relationship between Warehouse and Resource into a proper associative entity. Quantity is a fact about the pair (W_ID, Res_ID) — not about either entity alone — so it belongs here and not in either parent table. This satisfies the requirement for no partial dependencies.

4. Relief_Camp

Functional DependencyLeft side is superkey?Verdict
Camp_ID → Event_ID, Name, Location, Current_Occupancy, Max_CapacityYes — Camp_ID is PK✓ BCNF

The event's name and level are not stored in Relief_Camp — they are looked up via the foreign key. Storing them here would create a transitive dependency (Camp_ID → Event_ID → Event.Name), which would violate 3NF. We avoided this by keeping camp and event data in separate tables.

5. Dispatch_Log

Functional DependencyLeft side is superkey?Verdict
Dispatch_ID → Req_ID, W_ID, Dispatch_Time, Estimated_Arrival, StatusYes — Dispatch_ID is PK✓ BCNF
Req_ID → Dispatch_ID, W_ID, ...Yes — Req_ID is a candidate key (UNIQUE constraint)✓ BCNF

The UNIQUE constraint on Req_ID enforces the business rule that one request produces exactly one dispatch. Delivery details are separated into Delivery_Status to avoid mixing dispatch-time data (ETA, warehouse) with receipt-time data (actual arrival, receiver name). This separation keeps each table at one level of abstraction.

Summary

Normal FormRequirementStatus
1NFAll columns are atomic (no repeating groups or arrays). ENUM columns store a single value from a defined domain.✓ Satisfied
2NFNo partial dependencies — every non-key attribute depends on the whole primary key. All composite-key tables (Warehouse_Inventory, Request_Details) have attributes that describe the full key combination.✓ Satisfied
3NFNo transitive dependencies — non-key attributes do not depend on other non-key attributes. Event data is not repeated inside Relief_Camp; Resource data is not repeated inside Warehouse_Inventory.✓ Satisfied

Performance Indexes

Indexes are created on columns that are frequently used in WHERE clauses, JOINs, and ORDER BY operations. Without them, MySQL would do a full table scan for every dashboard query, which becomes slow as data grows.

Primary keys and UNIQUE constraints already create implicit indexes. The indexes below are additional ones defined in 02_indexes.sql.

Index NameTableColumn(s)Why it exists
idx_request_status Request Status Every dashboard query filters requests by status (Pending, Approved, etc.). Without this index, MySQL scans the entire Request table for each tab click.
idx_request_priority Request Priority The admin dashboard sorts and filters by priority. Warehouse managers also prioritize dispatch by urgency.
idx_request_camp Request Camp_ID The camp officer's dashboard filters all requests by their Camp_ID. This is used on every page load of the camp dashboard.
idx_request_time Request Request_Time Camp stats query counts deliveries in the last 7 days using a WHERE Request_Time > NOW() - INTERVAL 7 DAY clause.
idx_inventory_resource Warehouse_Inventory Res_ID fn_Total_Stock and sp_Approve_Request query inventory filtered by Res_ID across all warehouses. Called on every approval.
idx_inventory_warehouse Warehouse_Inventory W_ID fn_Check_Stock and sp_Dispatch_Request query inventory filtered by W_ID. Called on every dispatch.
idx_dispatch_status Dispatch_Log Status The admin overview counts in-transit dispatches. Warehouse dashboard filters dispatches by status.
idx_dispatch_time Dispatch_Log Dispatch_Time Dispatch history is displayed in chronological order. Without this index, sorting requires a full table scan.
idx_event_level Disaster_Event Level Admin stats query counts high/critical events. The events list is filtered and colored by level.
idx_event_status Disaster_Event Status Login page and admin overview filter events by Status = 'Active' on every load.
idx_stock_alert_open Stock_Alert Resolved, W_ID Composite index. The alerts query always filters by Resolved = FALSE AND a specific W_ID. Composite indexes are more efficient than two separate indexes for this AND condition.
idx_audit_table_time Audit_Log Table_Name, Changed_At Composite index for audit queries filtered by table name and ordered/filtered by time. Supports the ORDER BY Changed_At DESC LIMIT 20 query efficiently.
Total indexes: 12 explicit + implicit indexes from 13 PRIMARY KEY constraints + 4 UNIQUE constraints = 29 indexes total across the database.

Test Cases & Validation

The following test cases are defined in 09_test_cases.sql. They verify that constraints, triggers, procedures, and views all behave correctly. Each test has an expected result — a test passes if MySQL produces exactly that result and no unexpected side effects occur.

Test 1 — Negative Inventory Prevention (CHECK constraint)

Command: UPDATE Warehouse_Inventory SET Quantity = -50 WHERE Inv_ID = 1;
Expected: MySQL error 3819 — CHECK constraint chk_quantity_positive violated.
What it proves: Inventory can never go negative, even if the application layer sends a bad update.

Test 2 — Stock Alert Trigger Verification

-- Lower stock below the threshold
UPDATE Warehouse_Inventory SET Quantity = 5
  WHERE Res_ID = 2 AND W_ID = 1;

-- Verify the alert was auto-created
SELECT * FROM Stock_Alert WHERE Resolved = FALSE;
Expected: A new row appears in Stock_Alert with W_ID=1, Res_ID=2, Resolved=0.
What it proves: trg_after_inventory_update fires automatically when stock crosses the threshold — no application code needed.

Test 3 — Procedure Failure: Insufficient Stock

-- Create a request for 100,000 units — far more than available
INSERT INTO Request (CC_ID, Camp_ID, Status)
  VALUES (1, 1, 'Pending');
INSERT INTO Request_Details (Req_ID, Res_ID, Requested_Qty)
  VALUES (LAST_INSERT_ID(), 1, 100000);
CALL sp_Approve_Request(LAST_INSERT_ID());
Expected: SQLSTATE 45000 — "Insufficient total stock to approve this request." The procedure rolls back; Request.Status remains 'Pending'.
What it proves: The procedure correctly guards against approving requests the system cannot fulfil. The transaction is fully atomic — no partial updates leak through.

Test 4 — View Correctness: vw_Current_Inventory

SELECT * FROM vw_Current_Inventory
  WHERE Stock_Status != 'OK';
Expected: Returns only rows where Quantity < Min_Threshold with status 'LOW STOCK' or 'OUT OF STOCK'.
What it proves: The CASE expression in the view correctly computes stock status from live inventory data.

Test 5 — Audit Log Auto-Population

SELECT * FROM Audit_Log
  ORDER BY Changed_At DESC LIMIT 5;
Expected: Returns 5 rows showing every recent status change on the Request table. Each row includes old status, new status, the MySQL user, and timestamp.
What it proves: trg_after_request_status_update fires automatically on every status change — the audit trail is complete and tamper-proof.

Test 6 — Multi-Table JOIN Query (Manual Report)

This is a reporting query that demonstrates multi-table JOIN capability across 6 tables:

SELECT
    e.Name          AS Event,
    c.Name          AS Destination_Camp,
    r.Name          AS Resource,
    rd.Approved_Qty,
    d.Dispatch_Time,
    d.Status        AS Dispatch_Status
FROM   Disaster_Event e
JOIN   Relief_Camp     c   ON e.Event_ID  = c.Event_ID
JOIN   Request         req ON c.Camp_ID   = req.Camp_ID
JOIN   Request_Details rd  ON req.Req_ID  = rd.Req_ID
JOIN   Resource        r   ON rd.Res_ID   = r.Res_ID
JOIN   Dispatch_Log    d   ON req.Req_ID  = d.Req_ID
WHERE  e.Name = 'Cyclone Amphan' AND d.Status = 'Packed';
Expected: Shows all resources currently packed for dispatch to camps affected by Cyclone Amphan.
What it proves: The foreign key chain (Event → Camp → Request → RequestDetails → Resource → DispatchLog) is correctly set up and produces meaningful joined output.

Test 7 — Workflow Guard: Cannot Add Items to Approved Request

-- After sp_Approve_Request(1) has been called, try to add a new item
INSERT INTO Request_Details (Req_ID, Res_ID, Requested_Qty)
  VALUES (1, 3, 50);
Expected: SQLSTATE 45000 — "Cannot add items to a request that is not Pending." The trigger trg_before_request_details_insert blocks the insert.
What it proves: Once a request is approved, its line items are frozen. A camp officer cannot inflate a request after approval.
§ 18

Conclusion

DRAS demonstrates that a properly designed relational database can enforce complex real-world workflows entirely through its own constraints, without relying on the application layer for correctness.

What the database guarantees on its own

GuaranteeMechanism
Inventory never goes negativeCHECK constraint on Warehouse_Inventory.Quantity
Approved quantity never exceeds requested quantityCHECK constraint on Request_Details.Approved_Qty
One dispatch per requestUNIQUE constraint on Dispatch_Log.Req_ID
One delivery record per dispatchUNIQUE constraint on Delivery_Status.Dispatch_ID
No items added to non-pending requestsBEFORE INSERT trigger on Request_Details
Stock alert fires automatically on low stockAFTER UPDATE trigger on Warehouse_Inventory
Alert resolves automatically on restockAFTER UPDATE trigger on Warehouse_Inventory
Every status change is logged permanentlyAFTER UPDATE trigger on Request
Two simultaneous approvals cannot both succeed on the same stockSELECT … FOR UPDATE row-level lock in sp_Approve_Request
Camp officers cannot self-approve or modify inventoryMySQL RBAC — GRANT / REVOKE on application users

Design decisions and trade-offs

  • Procedure-only mutations: The choice to route all state changes through stored procedures (rather than direct application SQL) means every mutation gets consistent trigger coverage, audit logging, and transactional safety — at the cost of slightly more complexity in the database layer.
  • Global stock check at approval, warehouse check at dispatch: sp_Approve_Request checks total stock across all warehouses so approval is not blocked by distribution issues. sp_Dispatch_Request then checks the specific warehouse, which is a more precise constraint. This two-stage check reflects real-world logistics.
  • Separate Delivery_Status table: Delivery confirmation data (who received it, actual arrival time, condition) is kept in its own table rather than adding columns to Dispatch_Log. This keeps dispatch-time data and receipt-time data cleanly separated and avoids NULLs in the dispatch table for unconfirmed deliveries.
  • Audit_Log has no foreign keys: This is intentional. If audit records were linked to Request rows via foreign keys, deleting a request would cascade to the audit log and destroy the history. The log must be append-only and independent.
